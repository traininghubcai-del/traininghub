The ModelOne class = one page = one URL. Everything else is a lens on it.

The Hub used to be four separate screens — a public page, an Admin Hub, a Dealers Hub and an Edits & Updates hub. They were consolidated. Today there is one page per class, and who you are decides what you see on it. One QR code serves the dealer, the instructor and the administrator.

Public surface

No code required

  • Class list with search + month filter
  • Hover card with the full class description
  • Per-class registration form
  • Printable class sheet (QR + details)

Operations

Admin code

  • Edit any class field, two-pass confirmed
  • Add a class (inherits its branch's settings)
  • Full roster with contacts
  • Custom flier upload · reminder letters

Delivery

FSR code

  • Class-day roster and stats
  • Grade sheet: attendance, pass/fail, score
  • Two-step close-out with re-open
  • Printable sign-in sheet
Codes are verified on the server. The browser never holds the code list, and a locked lens is never sent the roster — unlocking is the server agreeing to release data, not the page revealing something it already had. Codes live in data/hub_codes.json; Admin is CORP7000 and FSR is MAA — separate codes, checked per lens, so neither one opens the other.

Key FlowsThe four paths that touch data

1 · A dealer registers

  • Opens /?event=<id> (link or QR)
  • Company typeahead resolves account # + TM silently
  • POST /api/register validates email, branch, attendees
  • Capacity checked inside the write transaction — the last seat can't go twice
  • Row → registrations.db, mirror → registrations.xlsx, entry → audit_log

2 · Admin edits or adds a class

  • Unlock Admin lens → edit fields
  • Save shows a diff and asks for the code again
  • Only changed fields are sent
  • Address → class_address.json; everything else → catalog via manage.py
  • ADD A CLASS needs only branch + name + date; the rest is inherited

3 · FSR runs and closes a class

  • Grading opens only once the class date has passed
  • Mark attendance, pass/fail, score, note per student
  • Step 1 Submit class info → locks
  • Step 2 Close class → final (re-openable)
  • A no-show can never be marked passed

4 · Reminders go out

  • Admin → Send reminders (PDF) → two confirmations
  • One personalised letter per student, streamed as PDF
  • Generating counts as sent — logged to the ledger
  • Same-day re-runs do not double-count
  • When email is wired in, it attaches to this same ledger

Rules & InvariantsDecisions the code enforces — break these and data goes wrong

RuleWhy
One catalog, one writer — only manage.py writes OFFICIAL_CLASS_SCHEDULE.xlsxTwo writers means silent divergence
Catalog writes are locked and atomicTwo overlapping saves corrupt the workbook — this was reproduced and fixed
Times are the branch's local time, always — 9:00 AM – 1:00 PM CST, never converted to the viewerA converted time puts a dealer at a branch an hour late
Class address is an overlay, not a columnVenue changes twice before a class; the schedule table shouldn't churn
Capacity is enforced inside the transactionChecking first is a race — both parties win the last seat
Locked lenses are never sent restricted dataOtherwise "unlocking" is theatre and PII sits in the page source
Every mutation is auditedWith several editors, a wrong edit must be traceable
A no-show never passesAttendance beats score, always
The public list hides past classesDealers can't register for something that already happened

VerifyDon't trust the app — test it

  ./.venv/bin/python tools/data_audit.py --server

30+ assertions, exit 0 = clean, read-only, safe any time. Run it after anyone edits the workbook. It checks:

Catalog & DB

  • Unique, non-blank event_id; required fields present
  • Dates parse; end time after start time
  • Every timed class states a timezone; one zone per branch
  • No orphan or childless registrations
  • No class overbooked; scores 0–100; no passed-while-absent
  • num_attending matches the attendee rows

Mirrors & live

  • Excel mirror row count matches the DB
  • No ghost classes in address / flier / reminder indexes
  • Every flier record has its file on disk
  • Public times show their zone; past classes hidden
  • Admin & FSR locked without a code
  • User payload carries no roster and no emails
