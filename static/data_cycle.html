M&A Training • Data Cycle

How your training data moves, lives, and comes back as action.

One record of truth behind every screen. This map walks the same information from the moment a dealer or TM fills out a form, into the database, out to the Admin and Dealer hubs, and eventually into monthly AI operations — training, dealer growth, and TM execution.

1

Capture — where data first enters

Forms · QR · spreadsheets · access keys

Dealers, techs, TMs and trainers create data when they register and attend; John's team adds context through the editable Excel lists.

Public & in-class
  • Landing / class page form → POST /api/register.
  • Registration QR on printed flyers (per class, in qr/).
  • Attendance QR for "today's class" planned
Internal sources (editable)
  • events.xlsx — class catalog.
  • dealers.xlsx · 2026 Program Dealers.xlsx — dealer directory & territories.
  • employees.xlsx — internal staff / TMs.
Access keys (the paid layer)
  • chat_config/tm_keys.yaml, trainer_codes.yaml — TM & trainer identities.
  • data/access_codes.xlsx — per-person login codes.
  • data/access_hub.json — billable-seat roster (each TM/Tier-1 dealer = one seat).
2

Store — the single source of truth

SQLite database + repository layer

Every input is normalized into one database (registrations.db) so there's one trustworthy record of classes, dealers, and people. Everything downstream is a view of this — never a scattered sheet.

Core tables
  • events — cache synced from events.xlsx (topic, date, branch, region, capacity).
  • companies — dealers / employers.
  • people — every individual (techs, TMs, trainers).
  • registrations — one row per company signup per class.
  • registration_attendees — one row per student seat.
What gets stamped
  • Territory Manager + branch per registration.
  • Per-student grading: attended, passed, score, comment, graded_by, graded_at.
  • Foreign keys link attendees → registrations → events & companies.
  • Backend is swappable — config.DB_BACKEND flips SQLite → Postgres with no app changes.
3

Enrich — turn raw rows into signals

Derived fields · statuses · mappings

The system adds meaning on top of raw rows so the UI can speak in human language — "seats remaining," "needs grading," "this dealer belongs to Alex."

Past class Today Upcoming
Per class
  • Seats taken / seats remaining (vs. capacity).
  • Status: upcoming · today · completed · canceled.
  • Grading status: graded vs. needs grades.
Per dealer / TM
  • Dealer ↔ TM / territory mapping.
  • Training history per dealer (classes, levels, dates).
  • Baseline KPIs that can become health scores later.
4

Use — who sees what, and where

Admin Hub · Dealers Hub · exports

Every role gets its own window into the same truth: trainers manage rosters, John and staff see the whole program, dealers see their progress, TMs see their territory.

Admin & staff — /admin
  • Full class list with color statuses.
  • Roster + per-student grading screens.
  • Excel export: GET /api/export.xlsx, plus a live mirror data/registrations.xlsx rewritten after every submit.
TMs & trainers
  • TM-filtered views — only their branches & dealers.
  • Trainer views — only classes they teach.
  • Region / teacher slicing for read-only tiers.
Dealers & techs — /dealers
  • Search by company + name + email.
  • Progress card: classes taken, level, next recommended step.
  • Retention quizzes & follow-up material planned
5

Feedback & AI — monthly operations on top

Dealer growth · TM execution

Because every action is stored and enriched in one place, the same data can power monthly operations: who needs a call, which class to push, which dealers are at risk, how each TM is performing.

Now — manual rules live
  • Filter to find "attended but not ordering," "empty seats," "dormant dealers."
  • Build TM to-do lists and executive exports.
Next — AI operations planned
  • Daily ranked lists: who to call, which class to promote.
  • Dealer health scores and TM scorecards.
  • Chatbot & agents sitting on this data instead of starting from scratch.

Why this map matters for the audit

  • Shows John that every portal and report reuses the same clean database — not random spreadsheets.
  • Makes it obvious where a bug or break would live: capture, store, enrich, use, or feedback.
  • Proves that "monthly AI operations for training, dealer growth, and TM execution" are just the final layer on a solid, already-built data cycle — not magic.
