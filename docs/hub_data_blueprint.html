Training Hub – Data Blueprint (Admin View)

M&A Supply · Internal data map · AUG_3 snapshot · 3 August 2026

How the Training Hub stores and uses data, from an Admin / back-office perspective: which files matter, what each operation reads and writes, and how a request flows through the system.

Read this first — the architecture changed. Earlier drafts of this document described four separate screens (Admin Hub, Dealers Hub, Edits & Updates hub, public page). Those were consolidated into the class page and deleted. If a document mentions /admin, /manage, /dealers, /api/admin-hub/*, /api/manage/*, src/access.py or access_hub.json as live, it is out of date — those all return 404 or no longer exist.

1. High-level architecture (admin mental model)

[ Browser ]
    static/index.html + static/app.js
    ONE page per class: /?event=<id>
    Three lenses on that page — User (open) · Admin (code) · FSR (code)

        │  HTTP
        ▼
[ Python HTTP server ]
    server.py  →  src/routes.py:Handler

        │  calls internal modules
        ├─ src/hub_modes.py       the three lenses + every gated action
        ├─ src/catalog.py         class catalog, read-only, from Excel
        ├─ src/manage.py          THE ONLY WRITER to the catalog (locked + atomic)
        ├─ src/registrations.py   validates a public signup
        ├─ src/db/sqlite_repo.py  the only module that imports sqlite3
        ├─ src/audit.py           append-only "who changed what"
        ├─ src/reminders.py       reminder history from the campaign ledger
        └─ src/reminder_letters.py per-student PDF letters

        │  reads / writes
        ▼
[ Data layer on disk ]
    data/OFFICIAL_CLASS_SCHEDULE.xlsx   classes + branches
    data/registrations.db               main training DB (+ audit_log)
    data/registrations.xlsx             live Excel mirror of the DB
    data/class_address.json             floating venue overrides
    data/fliers/                        one uploaded flier per class
    data/email_campaign/outbox.xlsx     reminder ledger
    data/dealers.xlsx                   program dealers (typeahead)
    data/employees.xlsx                 M&A personnel

  (design-time)
    _data_in/MASTER COPY ... _latest.xlsx   single human-edited master
    tools/build_from_master.py             compiles master → data/*.xlsx

The browser never talks to a database. Every request goes through typed Python modules that enforce structure and contracts — Excel headers, SQLite table shapes, and the access gate.

2. Data dictionary – key folders & files

2.1 Core data folder: data/

data data/OFFICIAL_CLASS_SCHEDULE.xlsx
Source of truth for classes. 73 classes.
  • events — one row per class. 19 columns: event_id, topic, region, branch, state, event_date, start_time/end_time, timezone, capacity, trainer, alt_trainer, track, event_location, host_label, notes, active, weekday, status.
  • branches — branch names mapped to territory manager; feeds branch dropdowns.
Read by src/catalog.py, src/manage.py, src/qr_pack.py, src/email_campaign.py — re-read on every request, never cached.
Written by src/manage.py only, under a lock, saved atomically.
data data/registrations.db
Primary training database (SQLite). Tables: events (cache), companies, people, registrations, registration_attendees (grading columns), class_log (close-out), audit_log (who changed what).
Read/write via src/db/sqlite_repo.py:SqliteRepository only.
This is the file to back up — it cannot be regenerated.
data data/registrations.xlsx
Live Excel mirror of registrations. Column order from config.COLUMNS, matching John's original sheet.
Written by src/export.write_registrations_xlsx() after every submit or removal. Read by humans only.
data data/class_address.json
Floating venue overrides. {event_id: "street address"}. Empty means "use the branch location". Deliberately not a catalog column, so a venue change never rewrites the schedule table.
Written by src/class_address.py (Admin lens). Delete it and every class falls back to its branch.
data data/fliers/
Per-class vendor artwork. Files named <event_id>.<ext> plus _index.json holding the original filename, size and upload date. JPG/PNG/WEBP/PDF, 8 MB cap, magic-byte validated.
Written by src/fliers.py (Admin lens).
data data/email_campaign/
Reminder engine state.
  • outbox.xlsx — the reminder ledger. One row per letter. Used for dedupe by the sender and for admin reporting.
  • campaign_schedule.xlsx — planned 7/3/1-day sends.
  • emails/ — generated HTML bodies + .ics invites.
Written by src/email_campaign.py and src/reminder_letters.log_generated().
Read by src/reminders.py for the per-class totals.
data data/hub_codes.json
Per-lens access codes. If absent, all three lenses use the built-in default (MMMAAA today). Change codes here — no code edit, no redeploy.
data data/dealers.xlsx · data/employees.xlsx
PII. 224 program dealers (feeds the company typeahead and resolves account # + TM) and M&A personnel. Both compiled from the master workbook.
Read by src/dealers.py.
legacy access_hub.json · access_codes.xlsx · edit_code.txt
Left behind by the removed access hub and edit-code system. Nothing reads them. Safe to delete.

3. Operation flows — what reads / writes what

3.1 Unlocking a lens

API POST /api/hub/unlock
Input: {mode, code} where mode is admin or fsr.
Backend: src/hub_modes.unlock() → verify(), which compares against data/hub_codes.json (or the built-in default).
Reads data/hub_codes.json
Writes nothing.
Note: the browser stores the accepted code in sessionStorage, so elevated access dies with the browser session. The code list itself never reaches the client.

3.2 Class list — public and admin

API GET /api/events  ·  GET /api/hub/classes?mode=admin&code=…
Backend: catalog.public_events() / hub_modes.classes_overview().
Reads OFFICIAL_CLASS_SCHEDULE.xlsx (classes, fresh) · registrations.db (seat counts, grading state, close-out) · email_campaign/outbox.xlsx (reminder history)
Writes nothing — pure read model.
Difference: the public list carries no counts. The admin overview adds registered/capacity, life-cycle status, last reminder date, reminder count and branch options.

3.3 Opening one class through a lens

API GET /api/hub/class?event_id=…&mode=…&code=…
Backend: hub_modes.class_payload().
Reads catalog · class_address.json · fliers/_index.json · and, only for Admin/FSR, the roster and grades from registrations.db.
Writes nothing.
The gate lives here. A locked lens is not sent the roster at all — it is not hidden in the payload for JavaScript to filter. Verified by the audit: the user payload contains no roster and no email addresses.

3.4 A dealer registers

API POST /api/register
Backend: registrations.build_registration() → SqliteRepository.save_registration(reg, capacity).
Reads catalog (to validate the class + capacity) · dealers.xlsx (resolve account # and TM from the company name)
Writes registrations.db (registrations, registration_attendees, companies, people, events cache) · registrations.xlsx (mirror) · audit_log
Capacity is enforced inside the write transaction (BEGIN IMMEDIATE), not before it. Checking first is a race — two people going for the last seat would both win.
Failure mode: if the xlsx mirror write fails, the DB row still committed; the server logs a warning and the registration stands.

3.5 Admin edits a class

API POST /api/hub/save-class
Backend: hub_modes.save_class() → manage.update_class().
Reads catalog (before-snapshot for the audit entry) · registrations.db (seats booked, so capacity can't drop below them)
Writes OFFICIAL_CLASS_SCHEDULE.xlsx (table columns) · class_address.json (address only) · audit_log
Two-pass: the UI diffs against the loaded values, shows exactly what will change, and asks for the code again. Only changed fields are sent, so a stale field can't overwrite someone else's edit.
Concurrency: the write is serialised by a lock and saved atomically (temp file + rename). Two overlapping saves previously corrupted the workbook.

3.6 Admin adds a class

API POST /api/hub/create-class
Backend: hub_modes.create_class() → manage.create_class().
Reads catalog — to inherit the branch's settled facts
Writes a new row in OFFICIAL_CLASS_SCHEDULE.xlsx · optional class_address.json · audit_log
Only three inputs are required — branch, class name, date. State, timezone, venue, host line, level and trainer are copied from the classes already running at that branch, so a new class arrives complete instead of half-blank.

3.7 FSR grades and closes a class

API POST /api/hub/grade · /api/hub/close-class · /api/hub/reopen-class
Backend: hub_modes.save_grades() / close_class() / reopen_class().
Reads roster + current grades from registrations.db
Writes registration_attendees (attended, passed, score, comment, graded_by, graded_at) · class_log.closed_at · audit_log
Rules enforced: grading opens only after the class date has passed; a student marked absent can never be marked passed; scores clamp to 0–100; an attendee id from another class is ignored; close-out is blocked while anyone is ungraded.
No email is sent. Closing is the finish line — when a provider is wired in, it attaches to close_class().

3.8 Admin generates reminder letters

API POST /api/hub/reminders → GET /reminder-letter?…
Backend: hub_modes.reminder_letters() → reminder_letters.log_generated() and render_pdf().
Reads catalog (class details) · roster from registrations.db
Writes email_campaign/outbox.xlsx (one row per letter) · audit_log
Generating counts as sent — there is no mail system, so a printed letter is the send. It writes to the same ledger the email sender uses, so both can never disagree.
One reminder = one day. Re-running the same day does not inflate the count.
PDFs are never written to disk — built in memory and streamed.

3.9 Admin removes a registration

API POST /api/hub/remove-registration
Backend: hub_modes.remove_registration().
Reads SqliteRepository.registration_snapshot() — the full record, captured before deletion
Writes deletes from registrations + registration_attendees · rewrites registrations.xlsx · audit_log (with the snapshot)
This is a hard delete. The audit snapshot records company, email, branch, seats and attendee names, so a removal is reconstructable — but it is not one-click undoable.

3.10 Custom flier

API GET/POST /api/hub/flier · GET /flier/<event_id>
Reads data/fliers/_index.json
Writes data/fliers/<event_id>.<ext> + index
Upload is base64 inside JSON (the stdlib server has no multipart parser, and cgi was removed in Python 3.13). Validated on extension and magic bytes, capped at 8 MB.
The public /flier/<id> route resolves the filename from the index, never from the URL, so the path cannot be walked out of data/fliers/.

4. The audit log — answering "who did that?"

Every mutation writes one append-only row to audit_log in data/registrations.db. It never raises (a logging failure must not fail a user's action) and app code never updates or deletes entries.

ColumnHolds
atISO timestamp
actorwhich lens acted — admin, fsr, public
actionclass.create, class.update, class.close, class.reopen, grades.save, reminders.generate, registration.create, registration.remove
targetevent_id
detailJSON — for edits, the before → after of each changed field; for removals, the full snapshot of what was deleted
ipclient address on public registrations

5. What to verify when several people have edit power

./.venv/bin/python tools/data_audit.py --server

30+ assertions, exit code 0 = clean, read-only, safe any time. Run it after anyone edits the workbook.

  • Excel contracts — OFFICIAL_CLASS_SCHEDULE.xlsx keeps its expected headers; unique non-blank event_id; dates parse; end time after start time; capacity numeric; every timed class states a timezone and each branch uses one zone.
  • DB contracts — SqliteRepository.init() runs at start and migrates missing columns; no orphan or childless registrations; every registration has a contact email; num_attending matches the attendee rows; no class overbooked; scores 0–100; nobody passed while absent.
  • Mirrors — registrations.xlsx row count matches the DB; no ghost classes in the address overlay, flier index or reminder ledger; every flier record has its file on disk.
  • Access — Admin and FSR both refuse without a code; the user payload carries no roster and no email addresses.
  • Audit — the audit_log table exists and is recording.
The one thing the app cannot protect you from: the catalog write lock is per-process. If John has OFFICIAL_CLASS_SCHEDULE.xlsx open in Excel while the server saves, Excel can still clobber it. Back up data/registrations.db and the catalog before any session where several people are editing.
