# Rule: One Catalog, One Registrations Doc

**Status:** Accepted · **Date:** 2026-07-13
Companion to [`ADR-classes-catalog.md`](ADR-classes-catalog.md) (this extends it to the
registrations side). Every claim below was verified against the code on 2026-07-13.

## What is true (ground-up shape)

### Class catalog
- **Single source:** `data/OFFICIAL_CLASS_SCHEDULE.xlsx`, sheet `events` (via `config.EVENTS_XLSX`).
- **Read path** — `src/catalog.py`: `load_catalog()` → `events_by_id`, `branches`, `branch_to_tm`;
  plus `public_events()`, `event_view()`, `missing_info()`, `event_cache_row()`.
  Used by: landing page, `/api/event`, registration validation, Admin Hub filters.
- **Write path** — `src/manage.py` (the `/manage` hub):
  - `list_classes(repo)` — all classes + seats taken/left.
  - `update_class(repo, event_id, fields)` — date / time / region / branch / location /
    capacity / notes / trainer / active.
  - `adjust_seats(repo, event_id, delta)` — capacity delta, never below `seats_taken`.
  - `set_active(repo, event_id, active)` — cancel / reinstate.
  - `create_class(repo, fields)` — append a new row with a unique `event_id`.

### Registrations
- **Truth:** `data/registrations.db` (schema: `src/db/schema.sql`) — tables `events`
  (cache of the catalog), `registrations`, `registration_attendees`, `companies`, `people`.
- **Flat "one doc" view:** `Repository.all_registrations_flat()` in `src/db/sqlite_repo.py`
  — joins `registrations` + `registration_attendees` + `companies` into one dict per row
  (`date_info`, `company_name`, `account_number`, `branch`, `territory_manager`,
  `num_attending`, `attendees`, attendance/grades, + internal ids).
- **Only Excel John opens:** `data/registrations.xlsx`, generated by
  `src/export.write_registrations_xlsx(repo)` from `all_registrations_flat()`.
  It **auto-regenerates** at server startup (`server.py`) and after every registration
  submit (`src/routes.py`) — no manual export step.
- Everything else (Admin Hub, Dealer Hub, email demos, APIs) already reads through
  `all_registrations_flat()`.

## The 4 rules

1. **Do not edit the `events` DB table directly.**
   All class edits go through `OFFICIAL_CLASS_SCHEDULE.xlsx` via `src/manage.py`.

2. **Do not create a second class catalog file for live data.**
   Old / demo catalogs live only in `_archive_data/`.

3. **Do not hand-edit `data/registrations.xlsx` or create siblings** (`registrations_final.xlsx`, …).
   It is always a generated view of the DB via `all_registrations_flat()`.

4. **Any feature that needs "all registrations + class info" must depend on
   `all_registrations_flat()`** (or a DB query that is provably equivalent) — never a
   separate Excel.

## Change flows (from the ground up)

**Classes:** John updates a class → do it in `/manage` (backed by `manage.py`) → the change
writes back to `OFFICIAL_CLASS_SCHEDULE.xlsx` → `catalog.load_catalog()` returns the new
values → new registrations cache them into the DB `events` table via `event_cache_row()` →
`all_registrations_flat()` + `data/registrations.xlsx` show the same story.

**Registrations:** public form / QR / Admin grading write **only** into the DB → after any
change touching registrations/grades, `write_registrations_xlsx(repo)` regenerates
`data/registrations.xlsx` (already wired to startup + each submit). John never hand-edits it.

## Mental shortcut

- **Class looks wrong?** → `OFFICIAL_CLASS_SCHEDULE.xlsx` + `/manage`.
- **Registration looks wrong?** → `registrations.db` + `all_registrations_flat()`, then
  regenerate `data/registrations.xlsx`.

Follow these and you have exactly one doc for classes (`OFFICIAL_CLASS_SCHEDULE.xlsx`) and
one for registrations (`data/registrations.xlsx`), both driven from the real catalog/DB —
never from random copies.
